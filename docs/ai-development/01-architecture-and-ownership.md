# 01 架构与文件所有权

## 1. 为什么需要“需求编译器”

PRD 是供人理解和评审的叙述文档；代码生成需要稳定 ID、明确版本、类型化字段和确定输入。直接把整篇 Markdown 反复交给 AI 会出现以下问题：

- 同一段话不同轮次被解释成不同接口；
- 修改一个词触发全量重写；
- AI 无法知道哪些历史已经发布；
- 生成文件和手写文件混杂，重新生成会覆盖人工工作；
- 需求变化后代码没有变化，但没有门禁发现；
- 未决 OD 被模型补成未经批准的默认规则。

因此采用两段式模型：

```text
产品 PRD
  │  扫描带 ID 条目、检测来源漂移
  ▼
经人工评审的结构化 spec/
  │  纯确定性校验、哈希、依赖、渲染
  ▼
generated/spec/ 契约视图、任务卡、Gherkin、追踪、requirements lock
  │  契约测试/验收测试失败
  ▼
人工或 AI 维护的业务实现代码
```

PRD 不直接驱动代码；结构化规格也不自动覆盖代码。工具保证该变化能被发现、定位、生成到契约和测试层，并阻止未同步合并。

## 2. 五类文件所有权

| 类型 | 当前/未来路径 | 谁能写 | 变化策略 |
|---|---|---|---|
| 权威规格 | `spec/**` | 经授权的人或 AI 起草、人工评审 | 新语义使用新版本文件 |
| 追加历史 | `spec/seals/**`、迁移、验收证据 | 专用命令或受控流程 | 首次创建后禁止覆盖 |
| 纯生成 | `generated/spec/**` | 仅 specgen | 每次可整体重新计算 |
| 一次性脚手架 | `specgen scaffold` 创建的新规格初稿 | 工具只创建缺失文件，之后人工/AI维护 | 文件存在时拒绝覆盖 |
| 手工实现 | 未来 `src/**`、人工测试、运行手册 | 工程团队和 AI | 生成器永不写入 |

不要在一个文件中混合生成区和手写区。需要扩展生成代码时，使用“生成基类/契约 + 手写实现”两个文件。

## 3. 三层哈希

### 3.1 PRD 来源条目指纹

扫描器识别 Markdown 表格首列 ID 和 `AC-*` 验收块。指纹包含：

- ID；
- 标题/规范正文；
- 所属章节；
- 来源类型。

行号不参与条目指纹，因此插入空行不会制造语义变化；整份文档哈希仍会变化，用于发现没有 ID 的叙述变化。

### 3.2 完整规格指纹

完整 JSON 经排序、无空白 canonical JSON 后计算 SHA-256。它用于：

- 生成 lock；
- 发现同版本原地修改；
- 固定发布选择；
- 绑定验收证据。

### 3.3 行为指纹

行为指纹排除版本、评审状态、标题、负责人等管理字段，保留业务正文、依赖、状态、权限、接口和测试语义。它用于判断 PATCH 是否改变行为。

## 4. 严格 JSON 边界

权威 JSON 加载器拒绝：

- 重复 key；
- `NaN`、`Infinity`；
- JSON 浮点 number；
- UTF-8 BOM；
- 非 Unicode NFC 字符串；
- 字符串中的 CR。

金额、测量值和需要精确定点语义的数字应保存为字符串，并由对应领域 Schema 约束精度和单位。

## 5. 确定性生成要求

- 不写动态生成时间、机器名、绝对路径或临时目录；
- 所有集合显式排序；
- UTF-8、LF、文件末尾一个换行；
- 文件名只来自严格校验的稳定 ID 和版本；
- 同一输入二次生成必须 `written=0`；
- lock 最后写入，表示一次生成完整结束；
- 只删除上一个 lock 明确拥有、且仍位于生成根目录内的旧文件；
- 遇到未知文件立即失败，不删除也不覆盖。

## 6. 当前安全边界

本地 SHA-256 和 Seal 链可以发现意外修改，但不能抵抗同时拥有文件写权限、能够重写整条历史链的攻击者。生产治理还应增加：

- Git 受保护分支；
- 必需评审人和 CODEOWNERS；
- CI 保存可信 Seal head；
- 组织签名或签名构建证明；
- 法规要求时使用 WORM/外部证据库。
